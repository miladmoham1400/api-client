# Phase-1 packaging and release

## Targets

Initial x64 baselines: Ubuntu 24.04 LTS and Windows 11. Produce Linux AppImage and deb, Windows NSIS installer. Other Linux distributions and Windows 10 are unverified until independently tested. macOS/ARM are out of scope.

Prefer target-OS native build runners because better-sqlite3 is native. A cross-generated installer is not proof of execution. Use the exact Electron ABI rebuild settings for the pinned builder. Keep runtime dependencies bundled; use userData for writable files. Application code/assets must be self-contained.

## Build and installation checks

Clean lockfile install -> type/lint/test -> bundled production build -> OS package -> install/launch -> SQLite write/reopen -> full offline local-API smoke story. Set publish disabled; do not upload or distribute automatically. No auto-update or telemetry.

Unsigned internal installers are acceptable for phase 1. Document potential Windows reputation prompts; do not claim code signing. Never advise disabling antivirus or system protections. Linux packaging must document distro prerequisites and use normal Electron sandbox configuration, not `--no-sandbox`.

Installer/uninstaller must not silently delete user workspaces. Preserve local userData on uninstall by default; provide documented path and explicit manual removal instructions for users who want full deletion. Avoid destructive commands in ordinary setup instructions.

## Release deliverables generated by implementation tasks

- Linux/Windows installable packages with version and SHA-256.
- `docs/toolchain-lock.md` with verified package/build versions.
- `docs/release-acceptance.md` with independent actual results for both OS targets.
- `docs/user-guide.md`: installation, workspace/request/variable workflow, save/draft behavior, secrets capability, upload re-selection, import/export limits and data location.
- `docs/known-limitations.md`: actual remaining issues and deferred features.

Do not mark phase 1 release-ready if either platform required checks are not run or fail. Coding completion and release verification are different states.

## Linux packaging implementation (TASK-028)

`electron-builder.json` configures unsigned x64 AppImage/deb with ASAR, explicit better-sqlite3 unpacking and builder-managed sequential native rebuild. `npm run package:linux` removes only generated `out/` and `dist/linux/`, builds and packages with `--publish never`. No runtime updater is added. Application identity remains `offline-api-client`, preserving its existing default userData directory. Required package homepage/maintainer fields use reserved `.invalid` internal placeholders; replace them with real project metadata before public distribution. The current package uses the default Electron icon.

Clean verification on Ubuntu 24.04 x64:

```text
npm ci
npm run lint
npm run test:unit
npm run package:linux
sha256sum dist/linux/*.AppImage dist/linux/*.deb
```

Initial npm/Electron/builder downloads require internet or prepared caches. Packaged users need no developer Node/npm. Native rebuilds must run sequentially; packaging restores the Electron binding after developer-Node unit tests. Linux desktop libraries and a working Electron sandbox are required. The generated deb declares GTK, notify, NSS, XSS, Xtst, xdg-utils, AT-SPI, UUID and libsecret dependencies; Ubuntu's t64 replacements may satisfy the legacy virtual package names. AppImage additionally needs working FUSE for its default mount mode, or the documented runtime extraction mode `APPIMAGE_EXTRACT_AND_RUN=1`. This environment has no `/dev/fuse`, so default FUSE launch is not verified. Do not use a sandbox-disable flag.

For test-only package selection, set `API_CLIENT_EXECUTABLE` to an absolute packaged executable/AppImage path and run `bash scripts/test-offline.sh`. For AppImage extraction-run also set `APPIMAGE_EXTRACT_AND_RUN=1`. The tests launch that executable with Chromium sandboxing, not the development Electron path; the integrated story asserts `app.isPackaged`. Run package suites sequentially because native chooser/keyboard automation shares the desktop. Temporary extraction of deb content is useful payload evidence but does not count as installation.

Administrative installation verification procedure: install the exact hashed deb with the OS package manager, launch `/opt/offline-api-client/offline-api-client` as a regular user, rerun the isolated full desktop suite and verify saved configuration after normal close/reopen. Then remove the application package and verify the same synthetic userData database remains; reinstall/reopen to verify it is usable. Removing this application must preserve `~/.config/offline-api-client/` (or `$XDG_CONFIG_HOME/offline-api-client/`). Never run installer/uninstaller verification against real user workspaces. Generated removal hooks manage application links/AppArmor only; inspecting them is not evidence that an actual uninstall was performed.

Current actual artifacts, hashes, checks and installation blockers are recorded in [TASK-028 report](task-reports/TASK-028.md). No Windows or phase-1 release-readiness claim follows from Linux payload checks.


The dedicated preservation check is separate from ordinary desktop smoke. Create a new `/tmp/api-client-task028-preservation-<alphanumeric suffix>` directory; set `API_CLIENT_PRESERVATION_DIR` to it, `API_CLIENT_EXECUTABLE=/opt/offline-api-client/offline-api-client`, and `API_CLIENT_PRESERVATION_PHASE=seed`, then run `bash scripts/test-offline.sh --config playwright.linux-preservation.config.ts`. After the seed closes normally, remove only the installed app package through the system package manager; verify the recorded database SHA-256 still matches. Reinstall the same hashed deb, set phase to `verify` and run the same check. It checks exact bytes before startup and logical saved workspace/request/environment/variable/theme after reopening. Authentication belongs in the OS prompt; never pass a password through commands, reports or chat. Keep these steps sequential and use only synthetic userData. Remove the temporary test directory after verification, never real user data.

TASK-028 verified actual deb install, installed offline suite, package removal and reinstall/reopen with identical synthetic userData. Default AppImage FUSE mount mode remains unverified. TASK-029 subsequently recorded independent Windows acceptance; see the [cross-platform acceptance record](release-acceptance.md), [user guide](user-guide.md) and [known limitations](known-limitations.md) for the current baseline.

## Windows packaging (TASK-029 — done)

On a native Windows 11 x64 machine, use the pinned developer Node/npm from `docs/toolchain-lock.md`. Install Visual Studio C++ Build Tools and Python if native SQLite compilation is needed. In PowerShell, from a clean checkout:

```powershell
npm.cmd ci
npm.cmd exec --no -- install-electron
npm.cmd run lint
npm.cmd run test:unit
npm.cmd run package:win
Get-FileHash .\dist\windows\offline-api-client-0.1.0-x64-setup.exe -Algorithm SHA256
```

Use `npm.cmd` because the default PowerShell execution policy blocks `npm.ps1`; do not change the policy. Do not run `npm audit fix`, which rewrites pinned versions. `package:win` refuses non-Windows or non-x64 hosts before changing outputs. Its Node script removes only generated `out/` and `dist/windows/`, runs TypeScript and production bundling, then invokes the installed builder with publishing disabled. The Windows configuration extends the existing packaging configuration and keeps ASAR, SQLite unpacking and sequential builder-managed native rebuild for Electron. Never run native rebuilds concurrently; the packaging rebuild follows developer-Node unit tests.

The configuration selects a per-user, one-click NSIS installer, leaves the app closed after installation and explicitly disables signing. Internal installers are unsigned and may trigger Windows reputation prompts. Actual Windows installation and acceptance are recorded in TASK-029; no code signing is claimed. Do not disable antivirus or system protections. Current default Electron icon and reserved internal metadata remain as documented above. Options were checked against the installed pinned builder's schema/source and its official [Windows documentation](https://www.electron.build/win/) and [NSIS documentation](https://www.electron.build/nsis/).

Install the hashed artifact, then launch the installed executable as a regular user. Record Windows version, developer and embedded Node versions, Electron ABI, actual native rebuild output, installer hash and installed executable path. Disconnect internet while keeping loopback available and verify every Windows row in `docs/testing.md` against local fixture APIs, including file/form sending and import/export dialogs. `API_CLIENT_EXECUTABLE` can select the installed executable for Playwright, but the Linux offline runner cannot provide Windows isolation, and Linux-only chooser tests skip Windows. **Windows test isolation:** the desktop specs isolate app data by setting `APPDATA`/`XDG_CONFIG_HOME`. Electron on Windows ignores `APPDATA` and resolves `userData` through the OS known-folder API, so a first Windows run (TASK-029 attempt 2) used the real `%APPDATA%\offline-api-client`. `tests/fixtures/desktop.ts` now passes `--user-data-dir=<APPDATA>\offline-api-client` on Windows for both development and packaged launches. The second-instance check in `tests/security.spec.ts` uses the same switch. A Windows spec without a temporary `APPDATA` fails instead of touching a real profile. Linux launch arguments are unchanged. This is test-only: production startup does not read the variable, and the switch is a standard Chromium/Electron command-line option. Confirmed on Windows on 2026-10-10: `tests/database.spec.ts` passed its temporary-directory assertion against the installed executable. A green suite with skips is insufficient: capture independent Windows evidence for those checks and normal close/reopen.

Uninstall preservation must use a separate Windows account with synthetic workspaces, never existing user data. Default Electron data is `%APPDATA%\offline-api-client\`; verify the actual path on the test machine. Close normally after saving, record database hashes and logical saved state, uninstall through Windows Settings, verify the data remains, reinstall the same hashed artifact and reopen it. `deleteAppDataOnUninstall: false` configures preservation; template inspection does not prove actual behavior. Do not pass the uninstaller's explicit data-deletion option during ordinary uninstall. Users wanting complete removal can explicitly delete that verified application data folder in Explorer after uninstall, understanding that it removes their workspaces and settings.
